## Problem statement

### Defect 1 — the branch gate reads the wrong branch

Story Q.u (v2.16.0) established that the out-of-sequence discipline is a false positive on a non-main branch: squash merges to main rewrite commit subjects into PR titles, so earlier `[Done]` stories no longer parse from `git log` even though they shipped. `_presume_committed_on_branch` replaced the hard error with two heuristics.

That relaxation keys on **where you are**, not **where the work is going**:

```python
# cli.py:2233
branch = _get_current_branch()
on_main = branch is None or branch in ("main", "master")
```

But gitbetter's optional positional `branch_name` **is** the start-a-new-branch signal — `git-push "msg" feature-xyz` creates the branch, commits there, pushes it. Starting a branch from `main` therefore evaluates `on_main = True` and takes the full direct-commit discipline, even though nothing lands on `main`.

On a squash-merged `main` that produces one of two wrong outcomes:

| Main's log | Result today | Should be |
|---|---|---|
| **Zero** `[Done]` IDs parse | No offenders → bundle offer proposes a subject covering *every* `[Done]` story in the file | Offer the last story, per the no-anchor heuristic |
| **Some** parse (recent direct commits), earlier ones don't | Out-of-sequence hard error, exit 1, no prompt | Anchor presumption, then the normal flow on the uncommitted tail |

**The irony is that the correct behavior already exists and is merely unreachable.** `_presume_committed_on_branch`'s no-anchor path already offers `Commit just the last one? [Y/n]` — precisely the "starting a branch should be simple and seamless" outcome. Nothing new needs inventing; the gate needs to consult the destination.

### Defect 2 — gitbetter's branch-work flags are unreachable

Both wrappers build their argv as:

```python
# cli.py:2310
argv = [tool_path, message]
if branch_name:
    argv.append(branch_name)
```

gitbetter exposes `--amend` and `--keep|-k`; **neither can be reached through project-guide**. `--keep` is exactly the multi-commit-feature-branch flag ("Skip the post-push cleanup prompt and leave the branch intact"). So today, sustained branch work through the wrapper means dropping to bare gitbetter and hand-typing the message the wrapper exists to derive — the convenience evaporates at exactly the moment the workflow gets long enough to need it.

### Defect 3 — completion staleness is narrower than its own evidence

Story R.f defined **stale** as the dead-path test only (`os.access(path, os.X_OK)`), and flagged the gap itself:

> A block generated by an older project-guide whose template has since changed is *not* detected, even though the version stamp R.d put in the block would make it detectable.

R.h inherited the gap and re-flagged it as "the last story where it would naturally land." It did not land. A user carrying a block generated before, say, R.d's bash-3.2 `complete … || complete …` fallback has a working-but-wrong install that `status` reports as healthy and `heal` never mentions.

## Findings that constrain the fix

### Finding 1 — gitbetter requires a message even under `--amend`

Confirmed from the installed source rather than the help text:

```bash
[[ ${#POSITIONAL[@]} -lt 1 ]] && { usage; exit 1; }          # git-push.sh:75
[[ -z "${COMMIT_MSG}" ]] && fail "Commit message cannot be empty after sanitisation."
...
run_cmd git commit --amend -m "${COMMIT_MSG}"                 # git-push.sh:247
```

There is no `--no-edit` path in amend mode (the `--no-edit` at line 274 belongs to a different flow — folding leftover changes in after a rejected push). Git itself would accept `--amend --no-edit`; **gitbetter will not**. So project-guide must supply a message on every amend. "Pass nothing through and let git keep the subject" is not available.

### Finding 2 — `--amend` is a short-circuit, not an inversion

The wrapper's normal contract is *already-committed → exit 0, "Nothing to commit."* Under `--amend`, already-committed is the **precondition** — left alone, the wrapper would exit 0 before ever invoking gitbetter and `--amend` would appear to do nothing.

The tempting fix is to invert that check and thread a new branch through the existing derivation flow. **That is the wrong shape.** Per the wrapper-value principle below, `--amend` means "commit the current tree on top of the old committed tree" — the message is *not* being decided, so none of the derivation machinery applies. `--amend` short-circuits the whole path: read the previous subject, apply the staging guard (Finding 5), refuse under `--no-input` (Finding 3), invoke gitbetter. A short distinct path rather than a new branch in a long one.

**Message source: preserve, never re-derive.** The previous subject is read with `git log -1 --pretty=%s` and passed straight back. Re-deriving it from `stories.md` was considered and rejected: it buys the ability to re-sync a subject after a story title changed, at the cost of silently rewriting a commit subject as a side effect of a bug fix. A developer who commits `R.q: gitbetter flag pass-through`, later assigns `v2.21.0` in the title, then amends a CI fix would get a rename they never asked for. Correcting a message is a bare-gitbetter task.

Preserved subjects came out of gitbetter and are therefore already sanitized (backticks stripped, double quotes converted), so re-passing them is idempotent. Preserve-only also removes a subtler hazard: `parse_committed_ids_from_subject` is permissive on read while `derive_bundle_commit_message` is strict on emit, so re-deriving a *legacy* bundled subject would silently canonicalize it.

### Finding 3 — `--amend` force-pushes

`git-push --amend` uses `--force-with-lease`. That makes history rewriting reachable through project-guide for the first time, in a tool whose stated constraint is that the developer owns all git operations and the LLM never commits. `--force-with-lease` refuses when the remote has moved, which bounds the blast radius — but it does not make the operation ordinary.

**Decision:** `--amend` is **interactive-only**. Under `--no-input` (or `CI=1`, or non-TTY stdin) it refuses with a non-zero exit rather than auto-proceeding. This matches the existing precedent that the out-of-sequence path never auto-yeses, for the same reason: a history-shape decision is a developer decision, not a CI default.

### Finding 4 — version-stamp comparison is the wrong staleness predicate

The obvious implementation of Defect 3 is "compare the stamped version to `__version__` and warn on mismatch." That would fire on **every** project-guide release, including the large majority that do not touch the completion template — turning a precise signal into background noise, which is the failure mode R.h explicitly refused to risk.

The predicate that matches the actual question ("would reinstalling change anything?") is a **content comparison**: regenerate the script from the parameters recorded in the installed block and compare against what is installed. The stamp's role is then diagnostic — it names *which* version generated the block in the warning — not decisional.

This is a genuine design question with an unproven half: the regeneration needs `--bin` and (for zsh) `--dir` recovered from the installed artifacts. R.f already reads the autoload directory out of the installed `fpath` line, so the precedent exists, but recovering `--bin` from a post-processed callback has not been done.

### Finding 5 — `--amend` will absorb the next story's work

gitbetter stages the whole tree before amending:

```bash
run_cmd git add -A "${GIT_ADD_PATHSPEC[@]}"     # git-push.sh:237
...
run_cmd git commit --amend -m "${COMMIT_MSG}"   # git-push.sh:247
```

So a developer who has finished R.q in the working tree and amends while the last commit is R.p lands **R.q's diff inside R.p's commit under R.p's message**. One coherent unit of work → one story → one commit is precisely the invariant this wrapper exists to serve, and an unguarded `--amend` walks straight through it.

The wrapper already computes the uncommitted `[Done]` list for its normal flow, so detection costs nothing. **Decision: refuse**, rather than prompt. This is the same class as the multi-story out-of-sequence hard error — attribution ambiguity is the trigger, and a prompt there would invite the wrong answer.

**Where the guard stops, deliberately.** It fires only on a `[Done]`-but-uncommitted story — the case project-guide has information about. In-progress work on a `[Planned]` story is invisible to it and will still be folded in by `git add -A`. That is correct: amending stages your tree, which is git's documented contract, and the wrapper does not become a general-purpose working-tree guard. It intervenes where `stories.md` gives it standing to, and nowhere else.

## The wrapper-value principle

Stated by the developer during planning, and load-bearing for every decision below:

> **The `project-guide` wrapper adds integration value — reading `stories.md` and `git log` so the developer copies and pastes less. Anything beyond that, use the bare `gitbetter` command.**

This is the test a proposed wrapper feature must pass. It resolves three questions in this subphase at once:

- **`--amend` passes the previous subject back** because fetching it from `git log` is exactly the copy/paste the wrapper exists to remove. It does **not** re-derive from `stories.md`, because at amend time no message is being decided.
- **`-m` / `--message` is out**, permanently and not merely for now: an explicitly supplied message is the case where the wrapper contributes nothing, which is the definition of "use the bare command."
- **The staging guard (Finding 5) is in**, because knowing which `[Done]` stories are uncommitted is `stories.md` information the bare command cannot have.

The principle also draws the line for future work: a proposed feature that neither reads `stories.md` nor reads `git log` does not belong in the wrapper.

## Decisions taken at planning time

| Decision | Choice | Rationale |
|---|---|---|
| **Branch gate** | Destination-aware: a supplied `branch_name` selects the presumption path | Smallest change; reuses Q.u's proven heuristics unchanged. The branch argument is an honest declaration of branch-PR intent |
| **Alternative rejected** | A `git_workflow: direct \| branch-pr` config field | More honest about the root cause, but adds a config field, doc surfaces, and a migration default to buy a distinction the branch argument already makes. Recorded as out of scope, revisitable |
| **`--keep`** | Straight pass-through | No project-guide semantics attach to it |
| **`--amend` semantics** | Commit the current tree on top of the old committed tree — nothing more | The wrapper-value principle. Anything beyond this is a bare-gitbetter task |
| **`--amend` message source** | Preserve `git log -1 --pretty=%s` verbatim; never re-derive | Finding 2 — re-deriving would rewrite a subject as a side effect of a bug fix, and would silently canonicalize legacy bundled subjects |
| **`-m` / `--message` override** | **Out**, by principle rather than by deferral | An explicitly supplied message is precisely the case where the wrapper contributes nothing |
| **`--amend` under `--no-input`** | Refuse, non-zero exit | Finding 3 |
| **`--amend` with an uncommitted `[Done]` story** | Refuse | Finding 5 — `git add -A` would fold that story's work into the previous story's commit |
| **Staleness predicate** | Content comparison, stamp used diagnostically | Finding 4 — a version compare would fire on every release |
| **Windows / git-bash** | **Dropped from this subphase** → Future | Neither outcome is validatable without a Windows machine; the gap is already documented in three places and unreported in the field |

### The destination-aware rule

> **When a `branch_name` argument is supplied, the work is destined for that branch — evaluate the committed-set the way Q.u evaluates a non-main branch, regardless of which branch you are standing on.**

Two boundaries fall out and must be settled during implementation rather than discovered:

- **`branch_name` equal to the current branch** is not branch work (`git-push "msg" main` while on `main`). The strict discipline should still apply.
- **Which branch name the announcements quote.** `_presume_committed_on_branch` prints `The first committed story in branch '<branch>' is: …`. The log actually scanned is the *current* branch's; the destination has no log yet. The message must name what was scanned, or it will mislead.

## Production concerns

- **`--amend` rewrites history and force-pushes.** Gated interactive-only (Finding 3). Under preserve-only messaging there is no old-vs-new subject to confirm, so the `--no-input` refusal plus the Finding 5 staging guard are the whole safety story.
- **A widened staleness predicate changes what `heal` warns on.** R.h's warning fires from the pre-invoke hook ahead of *every* command. Any false positive introduced here becomes noise on every invocation for every affected user. The content-comparison predicate exists specifically to keep the false-positive rate at zero; if it cannot be made exact, warning less is the correct failure direction.
- **The branch gate must not weaken direct-to-main discipline.** Out-of-sequence detection on `main` with no branch argument is unchanged. The relaxation is reachable only by explicitly naming a destination branch.
- **No new external dependency.** Both wrapper stories stay inside the established External CLI Dependencies pattern — discover via `shutil.which`, `subprocess.run(..., check=False)`, propagate the exit code.

Inside R-3 it rides `v2.21.0`. It must run **after** R.p–R.r, which change the very `features.md` / `tech-spec.md` surfaces it reconciles.

**No spike.** The uncertain half of R.r (recovering `--bin` from an installed block) is bounded enough to resolve inside the story; if it proves otherwise, R.r converts to an architectural spike at implementation time rather than being pre-emptively split.

## Out of scope

Each item below was raised and deliberately deferred — these are negotiation outcomes, not unilateral exclusions.

- **Windows / git-bash support or refusal.** R.i's recommended follow-on. Neither outcome can be validated without a Windows machine, and the "refuse" outcome would break any git-bash user who works today. The gap is documented in FR-7's known gaps, `install-options.md`, and the `v2.19.0` CHANGELOG. → **Future**.
- **A `git_workflow: direct | branch-pr` config field.** The more honest fix for Defect 1 — the strict discipline assumes commit subjects survive to main, which squash-merge breaks by construction. Deferred because the branch argument already carries the signal; revisit if the destination-aware gate proves insufficient.
- **`-m` / `--message` on `--amend`.** Excluded by the wrapper-value principle, not merely deferred — an explicitly supplied message is the case where the wrapper adds nothing over `git-commit --amend "msg"`. Revisiting it means revisiting the principle.
- **Re-deriving an amended commit's subject from `stories.md`.** Rejected in Finding 2. Correcting a commit message is a bare-gitbetter task.
- **Guarding in-progress work on `[Planned]` stories from `git add -A`.** The staging guard is scoped to `[Done]`-but-uncommitted stories (Finding 5). The wrapper does not become a general-purpose working-tree guard.
- **Adopting PR-based development in this repo.** Explicitly waived above, with no timeline.
- **fish completion, PowerShell, and bash 3.2 `compopt`.** The three remaining FR-7 known gaps, unchanged by this subphase.
- **Deleting `docs/specs/features_old.md`.** The R.s backup; removal is a housekeeping step for whenever that work closes, not a planned task.
